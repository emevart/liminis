# Архитектура

Карта модулей и одна граница, ошибка в которой не чинится малой кровью.

Решения — ADR-015 (форма ядра под WGSL) и ADR-034 (ядро свободная функция,
контракт процесса на слое оркестрации). Здесь их операционная часть: как
выглядит ядро, что вокруг него и что проверяется механически.

---

## Одна граница

Всё в `crates/liminis-core/` делится надвое.

**Ядро** переводится в WGSL построчно. Оно ничего не знает про конфиг, про
время, про то, кто его вызвал и сколько раз. Его входы — срезы плоских массивов
и `Copy`-структура параметров, его выход — одна ячейка.

**Оркестрация** знает всё остальное: какие буферы существуют, в каком порядке
идут процессы, сколько подшагов нужно каждому полю, куда писать счётчики
каналов. В WGSL она не уезжает никогда — это те примерно пятьдесят процентов
хост-кода, про которые ADR-024 говорит, что они там и останутся.

Граница проходит по вызову. Оркестрация вызывает ядро; ядро об оркестрации не
знает. Обратной стрелки нет.

## Карта модулей

```
crates/liminis-core/src/
    numeric/      типы M и Q, обёртки, таблицы трансцендентных
    world/        буферы полей, раскладка, двойная буферизация, LOD
    config/       схема сценария, валидатор, вывод масштабов и подшагов
    kernels/      ядра. Свободные функции. Форма под WGSL
    process/      трейт Process, порядок тика, диспетчеризация
    ledger/       счётчики каналов, сведение инварианта
    observe/      поток метрик, снапшоты
crates/liminis/
    src/main.rs   CLI
```

Зависимости идут в одну сторону: `kernels` тянет только `numeric`. Всё
остальное может тянуть `kernels`, но не наоборот. Если ядру понадобилось знать
про `config` — значит параметр не свёрнут на стороне хоста, и это ошибка.

## Форма ядра

Сигнатура фиксирована:

```rust
fn kernel(src: &[..], dst: &mut [..], p: &Params, idx: u32)
```

Срезы на вход, срез на выход, `Copy`-структура параметров, линейный индекс
вокселя. Возвращаемого значения нет: всё, что ядро сообщает миру, оно пишет в
выходной срез.

**Разрешено:** локальные скаляры, массивы фиксированного размера, `for` по
диапазону, ветвления, вызов других ядер-функций с той же формой.

**Запрещено:** `self`, трейты, дженерики по поведению, замыкания, `Vec`, `Box`,
`dyn`, `HashMap`, рекурсия, аллокации, чтение из того же буфера, куда идёт
запись, любая зависимость результата от порядка обхода.

**Параметры сворачиваются на хосте.** Ядро диффузии получает `alpha = D·dt/dx²`
одним числом и не знает ни `D`, ни `dt`, ни `dx` по отдельности. Это не
оптимизация: в WGSL параметры приходят uniform-буфером, и чем меньше в нём
величин, тем меньше мест, где масштаб может разъехаться.

## Gather, а не scatter

Воксель считает своё новое значение сам, читая соседей, и пишет только в свою
ячейку. Он никогда не пишет в чужую.

Соблазн обратный. ADR-005 формулирует сохранение как «вычли у донора, прибавили
акцептору», и напрашивается ядро, которое считает поток и применяет его к обеим
ячейкам. Так делать нельзя: на GPU это атомик на каждую грань, а результат
становится зависимым от порядка.

В gather-форме сохранение получается из **антисимметрии функции потока**:

```
flux(a, b) == −flux(b, a)   для любых a, b
```

Воксель `i` прибавляет себе `flux(here, neighbour)`, воксель `j` в том же
подшаге прибавляет себе `flux(neighbour, here)` — ровно противоположное. Сумма
по домену тождественно ноль, без единого атомика и без всякой синхронизации.

> **Антисимметрия держится на правиле округления.** Округление половин от нуля
> (`NUMERIC.md` §3) симметрично: `1.5 → 2`, `−1.5 → −2`. Округление вниз — нет:
> `floor(1.5) = 1`, а `floor(−1.5) = −2`. Возьми кто-нибудь `floor`, потому что
> это естественный выбор для целочисленного сдвига, и масса потечёт на каждой
> грани по единице — без единого падающего теста, зато с расходящимся ledger
> через несколько тысяч тиков.

Единственное исключение из «пиши только в свою ячейку» — счётчики каналов
ledger. Там атомарное сложение, и оно безопасно, потому что счётчики целые:
целочисленный атомик коммутативен, порядок не влияет (ADR-004).

## Скелет

```rust
// crates/liminis-core/src/kernels/diffuse.rs

use crate::numeric::{m_scale, M, Q};

/// Параметры одного применения. Только скаляры: в WGSL это uniform-буфер.
#[derive(Clone, Copy)]
pub struct DiffuseParams {
    pub nx: u32,
    pub ny: u32,
    pub nz: u32,
    /// D·dt/dx², свёрнуто на хосте. Ядро не знает ни D, ни dt, ни dx.
    pub alpha: Q,
}

/// Диффузия одного вещества в одном вокселе, один подшаг.
///
/// Читает `src`, пишет `dst[idx]` и больше никуда. Результат не зависит от
/// порядка, в котором ядро вызвано для разных `idx`.
#[inline(always)]
pub fn diffuse_voxel(src: &[M], dst: &mut [M], p: &DiffuseParams, idx: u32) {
    let here = src[idx as usize];
    let mut net = M::ZERO;

    for face in 0..6u32 {
        let n = neighbour(p, idx, face);
        net = net + flux(here, src[n as usize], p.alpha);
    }

    dst[idx as usize] = here + net;
}

/// Поток из `b` в `a`. Обязан быть строго антисимметричным при любых входах:
/// на этом, а не на тесте, держится сохранение (ADR-034).
#[inline(always)]
fn flux(a: M, b: M, alpha: Q) -> M {
    m_scale(b - a, alpha)
}
```

Оркестрация вокруг него:

```rust
// crates/liminis-core/src/process/diffuse.rs

impl Process for Diffuse {
    fn reads(&self) -> &[FieldRef] { &self.fields }
    fn writes(&self) -> &[FieldRef] { &self.fields }
    fn invariant(&self) -> Invariant { Invariant::ConservesMatter }

    fn apply(&self, world: &mut World) {
        for &s in &self.substances {
            let p = DiffuseParams { /* … alpha свёрнута здесь … */ };
            // Число подшагов выведено при загрузке конфига (ADR-030).
            for _ in 0..self.substeps[s] {
                let (src, dst) = world.pair_mut(s);
                for idx in 0..world.voxel_count() {
                    diffuse_voxel(src, dst, &p, idx);
                }
                world.swap(s);
            }
        }
    }
}
```

Трейт, циклы, владение буферами, подшаги, свёртка параметров — всё здесь.
В ядре ничего этого нет, и при порте на GPU внутренний цикл заменяется
диспатчем, а `diffuse_voxel` переписывается в WGSL построчно.

## Второй скелет: реакции

Диффузия — самое лёгкое ядро в системе: одно вещество, один скалярный параметр,
соседи по фиксированному стенсилю. На ней форма выглядит очевидной, и именно
поэтому одного скелета мало. Ядро реакций требует всех веществ вокселя сразу,
вектора коэффициентов переменной длины, переменного числа реакций и общего
коэффициента конкуренции — и всё это обязано уложиться в ту же сигнатуру, без
аллокаций и без трейтов (ADR-041).

Укладывается оно так: переменная длина уезжает в соседний плоский массив, а не в
тип, а локальные буферы получают границы сборки.

```rust
// crates/liminis-core/src/kernels/react.rs

use crate::numeric::{xi, Q};

/// Границы сборки. Локальные массивы ядра обязаны иметь фиксированный размер,
/// поэтому их приходится назвать; валидатор отвергает конфиг, который их
/// превысил (ADR-041).
pub const S_MAX: usize = 32;
pub const R_MAX: usize = 64;

/// Плоские таблицы реакций. Все read-only; в WGSL каждое поле — отдельный
/// `var<storage, read>`. Это именованный набор биндингов, а не интерфейс:
/// ни трейта, ни `dyn`, ни поведения внутри.
pub struct Rx<'a> {
    pub nu: &'a [i32],      // коэффициенты хранения подряд, все реакции
    pub nu_sub: &'a [u32],  // какому веществу принадлежит nu[j]
    pub begin: &'a [u32],   // начало реакции r в nu
    pub len: &'a [u32],     // длина реакции r
    pub e_r: &'a [u32],     // экспонента экстента реакции r (ADR-039)
}

/// Параметры одного применения. Только скаляры: в WGSL это uniform-буфер.
#[derive(Clone, Copy)]
pub struct ReactParams {
    pub n_voxels: u32,
    pub n_substances: u32,
    pub n_reactions: u32,
    pub tick: u32,
    /// Бит `s` — вещество `s` хранится в `i64` (ADR-040).
    pub width_mask: u32,
    /// Индекс энтальпии в векторе ν: она участник реакции наравне с веществом,
    /// иначе её приращение округлялось бы независимо (ADR-041). Номер приходит
    /// с хоста, а не назначается здесь — ADR-041 фиксирует «отдельная запись с
    /// зарезервированным индексом», конкретного числа в журнале нет.
    pub s_energy: u32,
    /// 1/V_voxel и dt, свёрнуты на хосте.
    /// V_voxel, а не обратная величина. Из `Δnᵢ = sᵢ·rate·dt·V` и
    /// `Δnᵢ = sᵢ·2^(−e_r)·ξ` следует `ξ = rate·dt·V·2^e_r`; со сдвинутым сюда
    /// `1/V` экстент уехал бы на `V²`, то есть на восемнадцать порядков в
    /// экорежиме, и ни один тест сохранения этого не увидел бы — `Δᵢ = νᵢ·ξ`
    /// точно при любом `ξ`.
    pub volume: Q,
    pub dt: Q,
}

/// Все реакции одного вокселя. Читает состояние N, пишет состояние N+1 и только
/// в свою ячейку: реакция локальна и соседей не касается вовсе.
pub fn react_voxel(
    src32: &[i32],
    src64: &[i64],
    dst32: &mut [i32],
    dst64: &mut [i64],
    energy_delta: &mut [i32],
    rx: &Rx,
    p: &ReactParams,
    idx: u32,
) {
    // 1. Спрос. Каждая реакция считает, сколько квантов экстента ей «хотелось
    //    бы», по одному и тому же снимку N, и сразу ограничивается по входам.
    //    Порядок реакций здесь не важен — это и есть цель.
    let mut want = [0i32; R_MAX];
    for r in 0..p.n_reactions as usize {
        // rate · dt · V_voxel · 2^e_r, округлённое стохастически. Единственная
        // конверсия Q → целое во всей химии (NUMERIC.md §1, ADR-027).
        let rate = rate_of(src32, src64, rx, p, idx, r);
        let raw = xi(rate, p.dt, p.volume, rx.e_r[r], rng_key(p.tick, idx, r as u32));
        want[r] = clamp_by_inputs(src32, src64, rx, p, idx, r, raw);
    }

    // 2. Коэффициент. Спрос суммируется по веществам; если какое-то перепродано,
    //    общий множитель — минимум по перепроданным. Домножать ξ безопасно:
    //    сохранение есть свойство вектора ν, а не величины ξ (ADR-027).
    let mut demand = [0i64; S_MAX];
    for r in 0..p.n_reactions as usize {
        accumulate_demand(&mut demand, rx, r, want[r]);
    }
    let scale = competition_scale(&demand, src32, src64, p, idx);

    // 3. Применение. Дельты копятся локально и пишутся один раз — иначе ядро
    //    читало бы из того буфера, в который пишет.
    let mut delta = [0i64; S_MAX];
    for r in 0..p.n_reactions as usize {
        let e = scale_extent(want[r], scale);
        if e == 0 {
            continue;
        }
        for j in rx.begin[r]..rx.begin[r] + rx.len[r] {
            let s = rx.nu_sub[j as usize] as usize;
            delta[s] += rx.nu[j as usize] as i64 * e as i64; // точно: ν целое
        }
    }
    for s in 0..p.n_substances {
        amount_store(dst32, dst64, p, idx, s, amount_get(src32, src64, p, idx, s) + delta[s as usize]);
    }

    // Энтальпия — такой же участник вектора ν, как вещество (ADR-041), но живёт
    // на 32³ (SPEC §1.5), а реакции идут на 128³. Поэтому приращение пишется
    // сюда, на мелкую сетку, в свою и только свою ячейку, а сворачивает его
    // отдельное ядро (ADR-045). Запись, а не прибавление: поле живёт внутри
    // одного тика, и обнулять его отдельным проходом не нужно.
    energy_delta[idx as usize] = delta[p.s_energy as usize] as i32;
}

/// Свёртка энергии 128³ → 32³. То же ядро под ту же сигнатуру, только линейный
/// индекс пробегает грубую сетку, а читает оно мелкую. Тоже gather: грубая
/// ячейка сама собирает свои шестьдесят четыре мелкие, и ни один атомик не
/// нужен (ADR-045).
///
/// Собирает два источника, а не один. Второй — поглощённый свет: поле `light`
/// уже хранится на 128³, поэтому `I[z] − I[z−1]` есть величина производная и
/// второго накопителя не требует (ADR-049). Хранить её отдельно значило бы
/// держать два источника истины об одном и том же.
pub fn fold_energy(
    energy_delta: &[i32],
    light: &[Q],
    src_h: &[i64],
    dst_h: &mut [i64],
    p: &FoldParams,
    coarse: u32,
) {
    let mut sum = 0i64;
    for fine in fine_cells_of(p, coarse) {
        sum += energy_delta[fine as usize] as i64;
        sum += absorbed_here(light, p, fine);
    }
    // Прежняя энтальпия читается из src_h, а не из dst_h: `dst[i] += …` было бы
    // чтением из буфера записи, запрещённым выше по этому документу.
    dst_h[coarse as usize] = src_h[coarse as usize] + sum;
}

/// Единственные два места, где разноширинность видна. Ветвление идёт по индексу
/// вещества, одинаковому для всех вокселей, поэтому на GPU переход единообразен
/// и варп не расходится.
#[inline(always)]
fn amount_get(src32: &[i32], src64: &[i64], p: &ReactParams, idx: u32, s: u32) -> i64 {
    let at = (s * p.n_voxels + idx) as usize;
    if p.width_mask & (1 << s) != 0 {
        src64[at]
    } else {
        src32[at] as i64
    }
}
```

Три вещи в этом скелете несущие, и все три легко потерять при переписывании.

**Снимок один на все реакции.** Спрос считается по состоянию `N`, применение
идёт в `N+1`. Стоит пересчитать наличие после каждой реакции — и порядок строк в
TOML начнёт менять прогон, причём невидимо: баланс продолжит сходиться, изменится
лишь то, кто съел субстрат первым. ADR-027 добивался устойчивости `reaction_id`
ровно от этого класса ошибок.

**Дельты копятся локально.** Прямая запись `dst[at] += …` внутри цикла по
реакциям — чтение из буфера записи, запрещённое выше по этому документу.

**`ξ_max` считается только по входам.** Потолок выхода — гарантия валидатора
через `max_conc` (ADR-039), а не кламп здесь. Продукт, перешедший объявленный
предел, означает неверное объявление, и падать надо громко.

## Что проверяется механически

**Система типов — первый рубеж.** `Q` не реализует `Deref` и не раскрывает
внутреннее поле, поэтому голый оператор над двумя `Q` не компилируется
(ADR-022). Это надёжнее любого линтера и работает без запуска.

**`kernel-lint` — второй рубеж.** PostToolUse-хук греплит `kernels/**` на
распаковку через `.0`, на арифметику над значениями, объявленными как `Q`, и на
запрещённые типы. Проверка сознательно неполна: полноту даёт тип, grep ловит
шаблоны WGSL, где системы типов нет.

**`numerics-reviewer` — третий.** Субагент, читающий дифф ядра против ADR-003,
005, 015 и 022. Вызывается перед принятием любой правки под `kernels/`.

Чего ни один из трёх не поймает: неверную антисимметрию. Функция потока,
написанная через `floor`, компилируется, проходит grep и выглядит правильно.
Ловит её только тест — сумма по домену до и после подшага, точное равенство.
Он обязан быть в приёмочных критериях S0, и он там есть.

## Что в `kernels/` не кладётся

Разбор конфига, вывод масштабов и подшагов, сведение инварианта, ввод-вывод,
порядок тика, выбор реализации процесса, работа с таблицей клеток как со
структурой. Всё это — оркестрация.

Правило проверки простое: если функцию нельзя переписать в WGSL построчно, не
меняя её смысла, ей не место в `kernels/`.

Первый файл в этом каталоге захлопывает заморозку спеки (ADR-032). Скелет и
карта — не ядро; они живут здесь, в `docs/`.
